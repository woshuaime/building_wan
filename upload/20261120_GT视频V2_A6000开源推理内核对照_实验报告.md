# GT 视频 V2 在 RTX A6000 上的开源推理内核对照

## 目的与环境

2026 年 11 月 20 日东京时间，在八栋留出验证全部退出后，使用同一张 RTX A6000 48 GB 对比可用于 Wan 视频推理的注意力与归一化实现。审核条件为输出逐值一致、相同输入上计时变快。测试沿用三轮最终权重、832×480 的 81 帧条件、30 步、CFG 5 和原种子 20261018。验证集和八条原成片保持只读。

本机使用计算能力 8.6、PyTorch 2.11.0+cu128、Triton 3.6。通过 GPU 对实际注意力输入的后端查询，确认 PyTorch 自动选择 Flash Attention。第三方包从官方发布物读取并在独立目录加载。xFormers 为 0.0.35，独立 FlashAttention-2 采用 Hugging Face kernels-community 的 torch211/cu128 构建，固定提交 `203236346cde5f75f47035f18f4baa8767c558f5`，动态库 SHA-256 为 `b2c63a5d07c3f6188690d37a22e76801309337f472257b7c2463831ff94213c8`。Liger-Kernel 使用 v0.8.5 源码。正式环境沿用原 PyTorch 及其依赖。[FlashAttention](https://github.com/Dao-AILab/flash-attention) · [kernels-community 构建](https://huggingface.co/kernels-community/flash-attn2/tree/203236346cde5f75f47035f18f4baa8767c558f5/build/torch211-cxx11-cu128-x86_64-linux) · [xFormers](https://github.com/facebookresearch/xformers/tree/v0.0.35) · [Liger-Kernel](https://github.com/linkedin/Liger-Kernel/blob/v0.8.5/src/liger_kernel/ops/rms_norm.py)

## 算子实测

注意力使用相同的随机 BF16 张量，形状为 batch 1、32,760 个 token、12 个头、每头 128 维，采用实际张量步幅、全连接的非因果注意力。每个候选预热 3 次，另做 9 轮随机交错排序的 CUDA 事件计时。下表为每次注意力的中位耗时，差异数为与默认输出逐元素比较的 50,319,360 个 BF16 值中不相等的个数。

| 注意力实现 | 中位耗时（毫秒） | 不同的 BF16 值 |
| --- | ---: | ---: |
| PyTorch 自动选择 | 59.604 | 0 |
| 显式指定 PyTorch Flash | 59.211 | 0 |
| xFormers 自动选择 | 59.075 | 0 |
| xFormers 指定 Flash | 59.273 | 0 |
| 独立 FlashAttention-2 | 57.724 | 96,272 |
| PyTorch cuDNN | 61.875 | 25,492,349 |
| PyTorch efficient | 112.566 | 25,487,100 |
| xFormers CUTLASS | 112.843 | 25,487,100 |

xFormers 默认在这里使用 PyTorch 所带的 Flash 实现，小幅时间波动不足以支持替换。独立 FA2 在这个算子上缩短约 3.2%，最大绝对差为 0.00024414，未达到本次逐值要求。差值本身不能衡量肉眼能否看出差异。

归一化使用完整 `1×32760×1536` 长序列、真实首个 DiT 块的查询归一化权重、两个随机输入种子。保持 Wan 的 FP32 计算和输出前 BF16 舍入位置，检查全部输出。下表为单算子用时；第一组交错计时 12 轮，最后一项另用 2 个种子和同组参考 2.666 毫秒复核。

| 归一化实现 | 中位耗时（毫秒） | 两个种子的差异数 |
| --- | ---: | --- |
| Wan 原实现 | 2.666 | 0 / 0 |
| Liger 官方 RMSNorm，Llama 舍入模式 | 0.309 | 232 / 181 |
| PyTorch 原生 RMSNorm 替换 | 0.402 | 12,942,118 / 12,989,209 |
| 保留原 PyTorch 归约、仅融合其余计算 | 1.039 | 0 / 0 |
| 本项目 Triton 内核，复现原 CUDA 归约顺序 | 0.447 | 0 / 0 |

最后一项按当前 PyTorch CUDA 的线程分配和加法次序实现，并在乘以权重前按 Wan 的位置舍入到 BF16。这个实现属于本项目，使用已经安装的 Triton。Liger 原版速度更快，按本次精度要求未启用。[PyTorch 2.11 CUDA 归约实现](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/native/cuda/Reduce.cuh) · [Triton](https://github.com/triton-lang/triton)

## 真实采样对照

使用留出建筑 6485、相同初始噪声、相同条件及权重。基准已包含前次通过验证的 VACE 条件复用、融合旋转和首层 CFG 复用。仅替换长序列 RMSNorm，每步在同一个 latent、时间步及文本条件上分别执行两种实现，交替谁先运行。耗时包含同步完成的正、负两次前向。前 4 步共有 8 份噪声预测，每份 2,096,640 个 BF16 值，均逐值相同。

| 采样步 | 基准秒/步 | 候选秒/步 | 正支/负支差异数 |
| --- | ---: | ---: | --- |
| 1，预热 | 9.7710 | 9.4945 | 0 / 0 |
| 2 | 9.7296 | 9.1236 | 0 / 0 |
| 3 | 9.8266 | 9.3043 | 0 / 0 |
| 4 | 9.8712 | 9.3164 | 0 / 0 |

3 个预热后采样步的中位耗时由 **9.8266 降至 9.3043 秒**，缩短 **5.31%**。每步新内核覆盖 266 次长序列归一化。按这个差额外推，30 步约省 **16 秒**；这个估算仅适用于采样，视频编码与校验另计。

## 全片对照与采用范围

随后在内存中生成建筑 6485 的全部 81 帧，与原队列已发布的无损三栏 MP4 中央预测区逐帧比较。采用准备接入项目的同一模块，真实命中 7,980 次归一化。共比较 **97,044,480 个 RGB 通道值，差异数为 0，最大绝对差为 0**。从读取原始条件到 VAE 解码耗时 292.34 秒，该时间不含模型加载及成品 MP4 编码，不能直接与旧队列的全栋出片时间相减。

新实现位于本实验的 `scripts/validation_rmsnorm.py`，通过 `validation_speed.py` 的原有配对选速入口生效。应用范围为本机 A6000、PyTorch 2.11.0+cu128、推理模式、原 Wan RMSNorm、连续的 1×32760×1536 BF16 长序列及匹配的冻结权重。其他输入继续走原路径。新队列在第 2、3 个真实步核对原始及候选的正负输出，预热后同一步耗时至少下降 2% 才启用候选。已发布的 8 条视频没有重编码或覆盖。全片逐值复核覆盖建筑 6485；其他建筑是否获得相同速度取决于实际计时。

接入后另取建筑 5466，通过正常 `ValidationSpeed` 入口执行前 4 个采样步。第 2、3 个时间步的正负预测仍逐值相同，自动选中加速。预热后该栋的原始路径双分支为 10.269 秒，包含前次优化和本次归一化的组合为 9.281 秒，缩短 9.62%。这个参照是原始实现，与前表“相比上次已优化版本再省 5.31%”使用的参照不同。该栋此次只做入口核验，没有另行生成整条视频。收尾 CPU 回归通过 298 项项目检查、19 项流水线检查和 31 项模型及验证检查。


## 2026-11-20　GT 视频 V2 播放偏色修复与交付清理

6485 的 81 帧逐值比较使用修复前的无损中央预测栏。现交付的八条视频已改成高质量 H.264 yuv420p，包含有损编码差异。后续若比较推理算法是否逐值等同，应在展示编码前比较 RGB 或模型张量。
