## 5. 复审问题闭环与新增验证

首轮复审评分为 82/100，发现三项未覆盖的缺陷：

1. argparse 接受 --ru，但入口通过检查字面量 --run 决定锁，缩写会绕过保护。两个入口现在先解析参数，依据 args.run 加锁。实际临时 CLI 测试证明 --run/--ru 在锁被占用时均拒绝进入验证；单元测试还覆盖 --r 和只读入口不打开锁。
2. 原短尾换算假设不足一个 batch 的组位于最后，但实际 dataloader 会 shuffle 分组。现策略：来源存在短组且只处理局部 epoch 时，拒绝推断样本量；目标 batch 会产生短组且游标在局部 epoch 时，拒绝推断 skip。完整 epoch 边界可以换算。当前 batch 1/2 对 1992 样本的换算不变；测试用短组先被取出的实际 _BatchDataset 验证拒绝，而非断言错误公式。
3. 暂停只查找独立 --output_path token，等号形式失败。现在兼容两种形式、空格、相对路径，并遵循最后一次参数值。

补测发现当前 scj Python 缺少 os.pidfd_open 和 signal.pidfd_send_signal；系统 /usr/bin/python3 有这两个 API。暂停仍在 scj 读取 checkpoint，停止时仅调用系统 Python 的纯标准库控制器。控制器在打开 pidfd 后核对启动时间及项目命令，再发信号；身份不匹配直接拒绝，控制失败不会伪报已停止。

新增验证已执行：工具测试 23 项、既有训练工具测试 12 项，均通过，无跳过。真实临时 CPU 进程只执行 sleep：验证只记录时仍存活、两种输出参数都可暂停并终止、错误启动时间被拒绝且进程仍存活。真实临时 CLI 验证了锁冲突，未调用模型推理。既有首轮的 14 项测试不能当作覆盖上述问题的证据。

本轮没有重新训练、生成模型视频或修改历史 checkpoint/缓存。对已发现的问题和对应验收场景没有遗留失败；项目整体的 GPU 端到端稳定性、历史训练终态和原生崩溃问题仍按第 4 节交接，不通过评分补造结论。

最后一次只读预检在原 PyTorch 头部读取路径退出时，捕获到额外的 `double free or corruption (out)` 文本。初次检查只要求失败为非零退出码，不能区分正常拒绝与原生崩溃，已修正这一验证缺口。当前先验证游标，再使用 safetensors 的 NumPy 后端检查权重头部；新增实际子进程测试证明成功预检不导入 torch，非法游标正常以退出码 1 拒绝。锁冲突测试同样严格要求正常失败码。新增工具测试现为 23 项，连同既有 12 项共 35 项，均通过，无跳过。此结果不证明 GPU 正式训练的原生堆错误根因已修复。
